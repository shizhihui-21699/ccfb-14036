# oram-store — 加密病历的隐蔽访问层

第三方云只存密文，但**访问模式**（哪条记录、频率、顺序、读还是写）本身就会泄露病情。
本系统用 **Path ORAM** 把访问模式也抹掉：云端日志里每次访问都是同构的
"读一条树路径 + 写一条树路径 + 两次定长状态写"，与逻辑读写、记录身份无关。

## 运行

```bash
cargo run --release
```

演示内容：朴素加密存储对照组 → ORAM 并发调阅（4 医生）→ 写回中途断电恢复 → 正确性抽检 → 攻击者视角日志分析 + 性能开销。

## 架构

```
医生端(客户端)                     模拟云端 (server.rs)
┌─────────────────────┐          ┌──────────────────────────┐
│ OramClient          │          │ 二叉树 bucket (加密块)     │
│  position map       │  读路径   │ 状态检查点 (加密, 定长)    │
│  stash (驱逐缓存)    │ ◄──────► │ position map 快照 (加密)   │
│  检查点/WAL 恢复     │  写路径   │ 租约锁 + 访问日志         │
└─────────────────────┘          └──────────────────────────┘
```

- `crypto.rs` — ChaCha20-Poly1305，每次写入随机 nonce（云端连"同一 bucket 被写两次"都看不出）
- `client.rs` — Path ORAM 核心：remap → 落检查点 → 读路径 → 驱逐写回 → 落检查点
- `server.rs` — 诚实但好奇的模拟云：稀疏 bucket 存储、版本化状态槽、TTL 租约、完整访问日志
- `analysis.rs` — 攻击者视角统计：卡方均匀性、热点、相邻碰撞、操作画像

## 关键设计取舍（性能 vs 隐蔽性）

| 决策 | 选择 | 代价/收益 |
|---|---|---|
| 树参数 | Z=4，树高 log₂N | N=100 万时每次访问 2×21×4 块 ≈ 174KB（1KB 块） |
| 块大小 | 1KB（可调） | 块越大放大越小：4KB 块时 ~44× |
| 客户端缓存 | stash + position map 全在内存 | 服务端观测行为与缓存内容无关，**缓存不构成泄露面** |
| 检查点 | 每次访问 2 次，64KB 定长填充档位 | 填充粒度即泄露粒度：只能看出"状态跨档"，看不出 stash 涨落 |
| position map | 客户端常驻（100 万条 = 4MB）+ 云端加密快照/增量 | 更大规模可递归套 ORAM（Recursive Path ORAM） |
| 多客户端 | TTL 租约 + 批处理（8 次/锁） | 简单互斥换吞吐；持锁者崩溃 → 租约过期 → 接管者先恢复再服务 |
| 崩溃恢复 | 先落检查点再访问，恢复时幂等重放写回 | 任何时刻断电：要么操作未发生，要么可重放完成，数据不乱 |

## 崩溃一致性论证

检查点在**读路径之前**原子写入（含 remap 记录 + stash + pending 叶子）：

- 断电于检查点前 → 操作从未发生，旧状态一致
- 断电于读路径/写回中途 → 恢复者见 pending，用检查点里的 stash 重读路径、重新驱逐写回（写回内容完全由 stash 决定，幂等）
- 断电于最终检查点后 → 干净完成

## 已知边界（演示未覆盖）

- 恶意云（回滚/重放状态）：需为检查点加单调计数器 + 客户端侧可信锚（如 SGX 或 TPM）
- 多客户端真并发（非互斥批处理）：需 Proxy ORAM / 分片 ORAM 架构
- 访问总量（侧信道）：长期总流量仍可见，可加入固定速率的 dummy 访问抹平
